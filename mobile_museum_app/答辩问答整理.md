# 掌上博物馆 — 答辩常见问题与参考答案

> 适用于课程设计 / 毕业设计答辩。答案基于本项目实际实现，请结合演示环境略作调整。

---

## 一、项目概述类

### Q1：请简要介绍你的项目。

**答：** 本项目是一款基于 **HarmonyOS（ArkTS + ArkUI）** 开发的「掌上博物馆」移动应用，专题聚焦 **海外藏中国瓷器**。系统采用前后端分离架构：App 通过 HTTP 调用 Flask 业务 API，后端结合 **Neo4j 知识图谱** 筛选专题文物、**MySQL** 存储详情与用户数据，并对接独立的 **知识问答子系统** 提供 AI 问答能力。主要功能包括文物浏览、搜索、以图搜图、登录注册、点赞收藏、评论、用户图片上传与内容审核、AI 智能问答等。

---

### Q2：为什么选择「瓷器」作为专题？能否扩展到其他文物？

**答：** 课设要求从知识图谱中选取**单类文物**作为展示主题。瓷器在海外馆藏中数量丰富、类型特征明确，便于在 Neo4j 中通过 `ArtifactType` 节点关系批量筛选。当前 `kg.py` 通过配置的 `THEME_TYPE_IDS` 查询瓷器相关 `(museum_id, object_id)` 对，再作为 MySQL 查询的过滤条件。若更换专题，只需修改类型 ID 配置并重新加载缓存，**无需改动 App 主体逻辑**，体现了专题与展示的解耦。

---

### Q3：你的项目和故宫博物院 App 等商业产品有什么区别？

**答：** 本项目的定位是**课程设计/学术研究型原型**，核心差异在于：
1. **数据来源**：依托组内共建的海外文物知识图谱 + MySQL，而非商业馆藏 API；
2. **专题聚焦**：当前仅瓷器一类，深度展示知识图谱筛选 + 多端协作；
3. **子系统集成**：对接组内问答子系统、图片服务、内容审核后台，体现**多子系统联调**；
4. **功能完整度**：已实现浏览、互动、审核、以图搜图等核心能力，但音视频讲解、华为账号登录、用户动态等仍为扩展项。

---

## 二、技术架构类

### Q4：请画出/说明系统的整体架构。

**答：** 系统分为四层：

```
┌─────────────────────────────────────────┐
│  HarmonyOS App（ArkTS）                  │
│  HomePage / SearchPage / DetailPage …   │
│  MuseumService + ApiClient + QaService  │
└──────────────┬──────────────────────────┘
               │ HTTP
┌──────────────▼──────────────────────────┐
│  Flask 业务 API（:5000，server/app.py）   │
│  Neo4j 专题筛选 + MySQL 详情/用户数据    │
│  内容审核引擎 + 以图搜图索引             │
└──────────────┬──────────────────────────┘
               │
     ┌─────────┼─────────┐
     ▼         ▼         ▼
  Neo4j     MySQL    图片API(:8000)
                       问答API(:8000)
```

- **App** 不直连数据库，所有业务经 REST API；
- **图片** 通过 `imgWeb` 字段走独立图片服务（8000 端口）；
- **AI 问答** 通过 WebView 嵌入问答组 H5，或原生 `QaChatPage` 调用问答 API。

---

### Q5：为什么前端选 HarmonyOS / ArkTS，而不是 Android 或 Flutter？

**答：** 1）课设明确要求基于 **HarmonyOS** 开发；2）ArkTS + ArkUI 是官方推荐技术栈，声明式 UI 适合卡片列表、详情页等场景；3）可复用系统能力，如语音识别（ASR）、TTS 语音讲解、相册选图等，已在搜索页语音输入、详情页语音讲解中落地。

---

### Q6：为什么后端用 Flask，而不是 Spring Boot 或 FastAPI？

**答：** 1）组内 Python 技术栈统一，与 Neo4j、PyTorch（以图搜图）、内容审核引擎对接方便；2）Flask 轻量，适合 REST API 快速迭代；3）本项目 API 以 CRUD + 业务编排为主，无复杂微服务治理需求，Flask 足够支撑。生产环境可平滑迁移到 FastAPI 等框架，接口契约不变。

---

### Q7：项目有几套后端服务？分别做什么？

**答：** 共三套：

| 服务 | 端口 | 职责 |
|------|------|------|
| Flask 业务 API | 5000 | 文物列表/详情、用户、互动、上传、审核 |
| 图片 API | 8000 | 文物高清图片 `/api/img` |
| 知识问答 API | 8000（独立部署） | Graph Agent + Neo4j 检索 + LLM 问答 |

App 通过 `Constants.ets` 中 `API_BASE`、`IMAGE_API_BASE`、`QA_API_BASE` 分别配置。

## 三、核心功能实现类

### Q8：首页文物列表的数据是怎么来的？

**答：** 流程为：
1. `HomePage.refreshAll()` 调用 `MuseumService.getArtifactsPage()` 和 `getHotArtifacts()`；
2. 请求 `GET /api/artifacts` 与 `GET /api/artifacts/hot`；
3. 后端 `kg.get_theme_filter_sql()` 从 Neo4j 获取瓷器专题的 `(museum_id, object_id)` 列表，生成 SQL 过滤条件；
4. MySQL 查询 `artifact` 表，按热度/年代/类型排序分页；
5. `image_resolver` 生成图片 URL，返回 JSON；
6. 前端 `ArtifactCard` 渲染双列卡片 + 热门轮播。

---

### Q9：Neo4j 和 MySQL 各自承担什么角色？为什么不只用一种数据库？

**答：**
- **Neo4j**：存储文物**语义关系**（文物—类型—朝代等），负责按「瓷器」专题**筛选范围**，体现知识图谱优势；
- **MySQL**：存储文物**结构化详情**（标题、描述、尺寸、图片路径）及**用户业务数据**（点赞、收藏、评论、上传图）；
- **分工原因**：关系查询适合图数据库，事务型用户数据适合关系型数据库，是常见的**图库 + 关系库**混合架构。

---

### Q10：热门排序（hot_score）如何计算？

**答：** 每件文物维护 `hot_score` 字段，由点赞数与收藏数汇总：`hot_score = like_count + favorite_count`（通过 `sync_artifact_hot_score()` 在用户点赞/收藏时同步更新）。首页「按热度」排序及热门轮播均基于此字段，使用户互动能反馈到推荐结果。

---

### Q11：以图搜图是如何实现的？

**答：**
1. 用户在搜索页选图，前端 Base64 编码上传；
2. `POST /api/artifacts/search-by-image`；
3. 后端 `image_search.py` 使用 **ResNet50** 提取查询图特征向量；
4. 与预构建的 `vectors.npy` 索引做**余弦相似度**匹配；
5. 命中结果回表查 MySQL 详情，按相似度排序返回；
6. 前端展示相似度与文物卡片。索引通过 `build_image_index.py` 离线构建。

---

### Q12：搜索功能支持哪些方式？

**答：**
- **文字搜索**：标题、描述、类型、文化字段模糊匹配；
- **朝代筛选**：多选朝代标签；
- **博物馆筛选**：按 `museum_id` 过滤；
- **语音搜索**：HarmonyOS ASR 将语音转文字后触发搜索；
- **以图搜图**：见 Q11。

---

### Q13：点赞、收藏、评论的完整流程是什么？

**答：** 以点赞为例：
1. 详情页点击「点赞」→ `requireLogin()` 检查登录；
2. `MuseumService.toggleLike()` → `POST /api/artifacts/{id}/like`，Header 带 `Bearer Token`；
3. 后端 `@require_auth` 校验 token，写入 `user_like` 表，更新 `hot_score`；
4. 前端更新按钮状态、Toast 提示，刷新个人中心。

收藏支持**收藏夹分组**；评论提交后走**内容审核**（见 Q15），审核通过才在公开展示区显示。

---

### Q14：用户上传图片的流程是什么？

**答：**
1. 详情页「用户图片」区选图、填写说明与地点；
2. `POST /api/user/photos`，图片 Base64 解码后存 `server/uploads/`；
3. 调用内容审核引擎评估风险；
4. 写入 `user_upload_photo` 表，默认 `status=0`（待审核）；
5. 个人中心可查看审核状态；`status=1` 后公开展示在文物详情页。

---

## 四、用户认证与安全类

### Q15：登录注册如何实现？密码如何存储？

**答：**
- **注册**：`POST /api/auth/register`，校验用户名、密码（≥6位）、邮箱或手机至少一项；密码用 **bcrypt** 哈希后存 MySQL `user` 表；
- **登录**：支持用户名/邮箱/手机号 + 密码，bcrypt 校验通过后生成 token；
- **Token**：`secrets.token_hex(24)` 生成，存服务端内存 `SESSIONS`，客户端 `UserSession` 内存保存；
- **鉴权**：需登录接口通过 `Authorization: Bearer <token>` 传递。

---

### Q16：Token 为什么只存内存？退出 App 就要重新登录？

**答：** 当前设计优先考虑**实现简单与安全**：不落本地持久化，避免 token 泄露风险；课设演示场景可接受。后续可扩展为加密存储 Preferences 或引入 refresh token 机制，属于可改进点。

---

### Q17：内容审核是如何做的？

**答：** 对接组内 **content-review-handoff** 审核引擎，与后台管理子系统共用 MySQL 中的 `sensitive_words`、`review_strategy_config`：
- **评论**：提交时算风险分；低风险自动通过、中风险待审、高风险拒绝且不入库；
- **图片**：默认待人工审核（`status=0`），写入 `auto_audit_score` 等字段供后台参考；
- 审核引擎不可用时，回退为「待审」策略，不阻断提交流程。

---

## 五、AI 问答类

### Q18：AI 问答功能如何实现？和主业务 API 是什么关系？

**答：** AI 问答由**独立的知识问答子系统**提供，与 Flask 业务 API 分离：
- App 首页/搜索页点击「AI问答」→ 跳转 `QaWebPage`，WebView 加载问答组 H5（`:5173`）；
- H5 内部连接问答 API（`:8000`），通过 **WebSocket 流式**或 `POST /api/qa/ask` 问答；
- 原生 `QaChatPage` 也已实现（`QaService` 调用 session/ask/history/feedback），可作为备选入口；
- 问答后端使用 **Graph Agent + Neo4j 知识检索 + LLM** 生成回答，并返回参考来源。

---

### Q19：问答时为什么要给问题加「瓷器」上下文？

**答：** `QaService.buildApiQuestion()` 会在用户问题未包含「瓷器」「文物」等关键词时，自动前缀「关于海外藏中国瓷器：」，以提高知识图谱检索命中率，避免泛化问题导致答非所问。

---

## 六、创新点与难点类

### Q20：本项目的创新点 / 亮点是什么？

**答：**
1. **知识图谱 + 关系库混合架构**：Neo4j 专题筛选 + MySQL 详情，体现语义与结构化数据分工；
2. **多子系统协作**：业务 API、图片服务、问答服务、内容审核后台分工联调；
3. **HarmonyOS 原生能力**：语音搜索、TTS 讲解、以图搜图、多图缩放；
4. **内容安全闭环**：用户 UGC（评论、图片）提交—机审—人工复审—公开展示；
5. **以图搜图**：ResNet50 特征 + 向量检索，贴近课设「图像检索」要求。

---

### Q21：开发中遇到的主要难点是什么？如何解决的？

**答：**
1. **模拟器访问本机 API**：模拟器不能用 `localhost`，需改为电脑局域网 IP → 在 `Constants.ets` 配置 `API_BASE`；
2. **Neo4j 不可用导致列表为空**：`theme_filter_or_error()` 会返回 503，需保证图数据库连通；
3. **图片跨服务加载**：列表接口返回 `imgWeb` 指向 8000 图片服务，前端 `toAbsoluteUrl()` 区分 API 基址；
4. **问答超时**：LLM 推理耗时长，单独设置 `QA_READ_TIMEOUT=120s`，并实现从历史恢复答案的容错；
5. **评论/图片审核联调**：通过 handoff 包统一审核算法，与后台管理共用配置表。

**答：**

### Q23：如果答辩现场演示连不上服务器怎么办？

**答：** 可提前准备：
1. 确认电脑与手机/模拟器在同一 WiFi；
2. 提前启动 `python app.py`、图片服务、问答服务；
3. 浏览器访问 `/api/health` 确认各组件 `ok`；
4. 备用方案：展示录屏 + 测试报告中的接口返回截图。App 离线时会明确提示「未连接服务器」，属于正常降级表现。

## 十一、各组员负责业务线答辩问答

> 按分工整理，每位同学重点准备自己负责模块的 3～5 题即可。

---

### 巫昊洋 — 文物浏览与详情展示

**负责范围：** `HomePage`、`ArtifactDetailPage`、`MuseumService` 列表/详情接口、热门轮播、多图展示与缩放、语音讲解。

#### Q1：你负责的「文物浏览」模块包含哪些页面和功能？

**答：** 主要包括：
1. **首页 `HomePage`**：瓷器专题列表（双列卡片）、热门文物轮播、按热度/年代/类型排序与分页；
2. **详情页 `ArtifactDetailPage`**：文物完整属性、多图 Swiper 轮播、全屏捏合缩放、语音讲解（TTS）；
3. **数据层**：通过 `MuseumService.getArtifactsPage()`、`getHotArtifacts()`、`getArtifact()` 调用后端 API。

#### Q2：首页列表的数据请求流程是怎样的？

**答：** `HomePage.aboutToAppear()` → `refreshAll()` → 并行请求：
- `GET /api/artifacts?sort&page&size` 获取分页列表；
- `GET /api/artifacts/hot?size=8` 获取热门推荐；
后端先用 Neo4j 筛选瓷器专题范围，再查 MySQL，经 `image_resolver` 生成图片 URL 返回；前端用 `ArtifactCard` 渲染，连接成功时显示「知识图谱·瓷器 · 共 N 件」。

#### Q3：文物详情页展示了哪些信息？图片如何处理？

**答：** 详情包含标题、朝代、年代、类型、材质、尺寸、馆藏、描述、来源等字段。图片方面：
- 接口 `GET /api/artifacts/{museumId}/{objectId}` 返回 `imgsWeb` 多图列表；
- `MuseumService.getImageList()` 拼接 `IMAGE_API_BASE` 绝对地址；
- 支持轮播切换、全屏模式、双指缩放与双击放大；
- 进入详情时调用 `kg.is_in_theme()` 校验该文物属于瓷器专题。

#### Q4：热门轮播的数据从哪来？和列表排序有什么关系？

**答：** 热门数据来自 `GET /api/artifacts/hot`，后端按 `hot_score` 降序取前 N 条。`hot_score` 由用户点赞数与收藏数汇总，与列表「按热度」排序使用同一字段，保证热门区与列表排序逻辑一致。

#### Q5：你模块里用了哪些关键前端组件/文件？

**答：**

| 文件 | 作用 |
|------|------|
| `HomePage.ets` | 首页列表、排序、分页、热门轮播 |
| `ArtifactDetailPage.ets` | 详情展示、多图、语音讲解 |
| `ArtifactCard.ets` | 列表卡片组件 |
| `MuseumService.ets` | `getArtifactsPage`、`getHotArtifacts`、`getArtifact` |
| `server/app.py` | `/api/artifacts`、`/api/artifacts/hot`、详情接口 |

### 侯程耀 — 搜索与分类发现

**负责范围：** `SearchPage`、关键词/朝代/博物馆筛选、语音搜索、搜索 API、元数据接口。

#### Q1：你负责的搜索模块支持哪些检索方式？

**答：**
1. **文字搜索**：输入名称或关键字，调用 `GET /api/artifacts/search?q=...`；
2. **朝代筛选**：多选朝代标签，参数 `dynasty=...`；
3. **博物馆筛选**：多选博物馆，参数 `museum_id=...`；
4. **语音搜索**：`SpeechSearchService` 将语音转文字后填入搜索框并触发检索；
5. 条件可组合使用，支持分页。

#### Q2：搜索时如何保证结果仍在「瓷器」专题范围内？

**答：** 后端 `search_artifacts()` 首先调用 `kg.get_theme_filter_sql()` 获取 Neo4j 专题过滤条件，再叠加关键词、朝代、博物馆等 `AND` 条件。即：**先限定瓷器专题，再在专题内搜索**，不会搜到其他类型文物。

#### Q3：朝代和博物馆列表数据从哪获取？

**答：** 搜索页 `aboutToAppear()` 时并行加载：
- `GET /api/dynasties` → 朝代 Chip 列表；
- `GET /api/museums` → 博物馆 Chip 列表；
均由 `MuseumService.getDynasties()`、`getMuseums()` 封装，数据来自 MySQL 中已入库文物的去重统计。

#### Q4：语音搜索是如何实现的？

**答：** 使用 HarmonyOS 系统 **ASR（语音识别）** 能力，封装在 `SpeechSearchService.ets`：
1. 用户按住麦克风按钮开始听写；
2. 识别结果通过回调写入搜索框 `keyword`；
3. 自动调用 `doSearch()` 发起 API 请求；
需在真机/模拟器授予麦克风权限，并安装中文语音包。

#### Q5：搜索无结果或用户未输入时怎么处理？

**答：** 前端校验：若关键字、朝代、博物馆均为空，则不发起请求；有搜索过但结果为 0 时显示「共找到 0 件」。后端若全部条件为空返回 400 提示「请输入关键词、朝代、类型或博物馆」。

### 王希童 — 用户注册登录与会话

**负责范围：** `LoginPage`、`RegisterPage`、`UserSession`、`MuseumService.login/register`、后端 auth 接口。

#### Q1：你负责的用户认证模块包含哪些功能？

**答：**
1. **注册**：用户名 + 密码（≥6位）+ 邮箱或手机号（至少一项）；
2. **登录**：支持用户名/邮箱/手机号任意一种 + 密码；
3. **会话管理**：`UserSession` 内存保存 token 与用户信息；
4. **登录引导**：详情页、个人中心在需登录操作时跳转 `LoginPage`；
5. **退出**：个人中心清除本地会话（无服务端 logout 接口）。

#### Q2：注册和登录的后端流程分别是什么？

**答：**
- **注册** `POST /api/auth/register`：校验参数 → bcrypt 哈希密码 → INSERT `user` 表 → 生成 token 写入 `SESSIONS` → 返回 token + user + stats，**注册即自动登录**；
- **登录** `POST /api/auth/login`：按 account 查 user 表 → bcrypt 校验 → 检查 `status=1` → 更新 `last_login_at` → 写 `login_logs` → 生成 token 返回。

#### Q3：Token 如何生成和传递？为什么退出 App 要重新登录？

**答：** 服务端用 `secrets.token_hex(24)` 生成随机 token，存内存字典 `SESSIONS[token]=user_id`。客户端 `UserSession.saveLogin()` 仅存内存，后续请求由 `ApiClient` 自动附加 `Authorization: Bearer <token>`。当前**未做本地持久化**，进程结束即失效，属于课设阶段的简化设计。

#### Q4：未登录用户访问需登录功能时如何处理？

**答：** 详情页 `requireLogin()` 弹出对话框：「需要登录」→ 用户可选「稍后再说」或「前往登录」；个人中心未登录时仅展示浏览记录（本机），收藏/点赞等 Tab 提示「请先登录后查看」。

#### Q5：你模块涉及哪些核心文件和接口？

**答：**

| 类型 | 文件/接口 |
|------|-----------|
| 页面 | `LoginPage.ets`、`RegisterPage.ets` |
| 会话 | `UserSession.ets` |
| 服务 | `MuseumService.login()`、`register()` |
| 后端 | `POST /api/auth/login`、`POST /api/auth/register` |
| 鉴权 | `server/app.py` 中 `@require_auth`、`SESSIONS` |

### 甘博宁 — 用户点赞、收藏与评论互动

**负责范围：** 详情页互动区、点赞/收藏/评论 API、`ProfilePage` 互动数据展示、收藏夹、内容审核展示。

#### Q1：你负责的互动模块包含哪些功能？

**答：**
1. **点赞**：详情页一键点赞/取消，同步 `user_like` 表与 `hot_score`；
2. **收藏**：支持收藏/取消，可选**收藏夹分组**存放；
3. **评论**：发表评论、回复他人评论、删除自己的评论；
4. **状态查询**：进入详情时加载当前用户是否已赞/已藏；
5. **个人中心**：展示我的点赞、收藏、评论列表及审核状态。

#### Q2：点赞后为什么首页热门会变化？

**答：** 点赞/取消时后端调用 `sync_artifact_hot_score()`，按该文物的点赞数 + 收藏数更新 `artifact.hot_score`。首页「按热度」排序和热门轮播均依赖此字段，形成**用户行为 → 热度 → 推荐**的闭环。

#### Q3：收藏夹功能是如何实现的？

**答：**
- 表：`user_favorite_folder`（收藏夹）、`user_favorite`（收藏记录，含 `folder_id`）；
- 收藏时若无收藏夹则直接收藏；若有则弹出选择器，可新建收藏夹；
- 接口：`GET/POST /api/user/favorite-folders`、`PUT .../favorite-folder` 移动文物到指定夹；
- 个人中心可按收藏夹 Tab 筛选查看。

#### Q4：评论提交后为什么不一定立刻显示？

**答：** 评论经 **content-review-handoff** 审核引擎处理：
- 低风险 → `audit_status=1` 自动通过，立即公开展示；
- 中风险 → `audit_status=0` 待人工审核，个人中心显示「待审核」；
- 高风险 → 拒绝且不入库，返回 `rejectReason`；
详情页 `GET .../comments` 仅返回已通过评论。

#### Q5：你模块的关键接口有哪些？

**答：**

| 功能 | 接口 |
|------|------|
| 互动状态 | `GET /api/artifacts/{id}/status` |
| 点赞 | `POST/DELETE .../like` |
| 收藏 | `POST/DELETE .../favorite` |
| 移动收藏夹 | `PUT .../favorite-folder` |
| 发表评论 | `POST .../comments` |
| 删评论 | `DELETE /api/user/comments/{id}` |
| 我的点赞/收藏/评论 | `GET /api/user/likes`、`favorites`、`comments` |

### 陆俊龙 — 用户上传与个人内容管理

**负责范围：** 详情页用户图片上传、`ProfilePage` 个人中心、审核提醒、浏览历史、待审内容管理。

#### Q1：你负责的个人内容管理包含哪些模块？

**答：**
1. **用户图片上传**：详情页选图、填写说明与地点，关联当前文物；
2. **个人中心 `ProfilePage`**：收藏、点赞、评论、上传图片、浏览记录；
3. **审核状态查看**：待审评论/图片计数、黄色提醒条、一键跳转；
4. **浏览历史**：本机 `BrowseHistoryStore` 记录最近浏览文物；
5. **账号面板**：`ProfileAccountPanel` 展示用户信息与待审摘要。

#### Q2：用户上传图片的完整流程是什么？

**答：**
1. 详情页「用户图片」→ `ImagePickerUtil` 选图转 Base64；
2. 填写说明（必填）、地点（选填）→ `requireLogin()` 校验登录；
3. `POST /api/user/photos`，Body 含 `imageBase64`、`description`、`location`、`museumId`、`objectId`；
4. 后端解码存 `server/uploads/`，调用审核引擎，写入 `user_upload_photo`（默认 `status=0` 待审）；
5. 审核通过（`status=1`）后，该图在详情页公开展示区可见。

#### Q3：个人中心如何展示和管理用户内容？

**答：** `ProfilePage.refresh()` 登录后并行拉取：
- 收藏（可按收藏夹筛选）、点赞、我的评论、我的图片；
- `updatePendingCounts()` 统计 `auditStatus=0` / `status=0` 的待审项；
- `ProfileAccountPanel` 有待审时显示黄色提醒条，点击跳转「我的内容」Tab；
- 点击已通过项可进详情；未通过项弹窗显示 `rejectReason`。

#### Q4：浏览记录存在哪里？为什么不同步到服务器？

**答：** 浏览记录由 `BrowseHistoryStore` 存于**本机 Preferences**，在详情页 `loadAll()` 时调用 `MuseumService.recordBrowse()` 写入。当前设计侧重课设快速实现与隐私简化，未做账号级云同步，属于可扩展项。

#### Q5：上传的图片和评论审核状态有哪些？用户如何感知？

**答：**

| 类型 | 状态码 | 含义 | 用户感知 |
|------|--------|------|----------|
| 评论 | `audit_status=0` | 待审核 | 个人中心黄色提醒 |
| 评论 | `audit_status=1` | 已通过 | 详情页公开展示 |
| 图片 | `status=0` | 待审核 | 个人中心「N 张图片等待审核」 |
| 图片 | `status=1` | 已通过 | 详情页用户图片区展示 |
| 图片 | `status=2` | 已拒绝 | 点击查看 `rejectReason` |

### 薛度扬 — 以图搜图与组内/组间联调

**负责范围：** `image_search.py`、搜索页以图搜图、`Constants.ets` 多服务配置、子系统联调文档与测试。

#### Q1：你负责的以图搜图功能是如何实现的？

**答：**
1. 用户在 `SearchPage` 从相册选图 → `ImagePickerUtil` 转 Base64；
2. `POST /api/artifacts/search-by-image`，Body：`{ imageBase64, page, size }`；
3. 后端 `image_search.py` 用 **ResNet50** 提取查询图特征向量；
4. 与离线构建的 `data/image_index/vectors.npy` 做**余弦相似度**检索；
5. 命中 `(museum_id, object_id)` 回表查 MySQL 详情，按相似度排序返回；
6. 前端卡片展示相似度分值。

#### Q2：图像索引是怎么建立的？什么时候需要重建？

**答：** 运行 `server/build_image_index.py` 离线脚本：遍历专题内文物图片，ResNet50 提特征，写入 `vectors.npy` + `meta.json`。当文物库新增/更换图片、或切换专题时，需重新构建索引；`/api/health` 中 `imageSearchIndex` 字段可检查索引是否就绪。

#### Q3：本项目涉及哪些子系统？你如何完成组间联调？

**答：** 共协作 **4 个子系统**：

| 子系统 | 端口 | 对接内容 |
|--------|------|----------|
| 掌上博物馆业务 API | 5000 | 本组 Flask `app.py` |
| 图片服务（Web 组） | 8000 | `IMAGE_API_BASE`，`/api/img` |
| 知识问答（问答组） | 8000 | `QA_API_BASE`，AI 问答 |
| 内容审核（管理组） | 共用 MySQL | `content-review-handoff` 引擎 |

联调步骤：确认同一校园网 → 各服务 `/health` 通过 → 修改 `Constants.ets` 三台地址 → App 端逐项验证列表、图片、问答、审核。

#### Q4：联调时最常遇到什么问题？怎么排查？

**答：**
1. **模拟器连不上 API**：`localhost` 不可用，改局域网 IP；
2. **图片不显示**：列表走 5000，图片须走 `IMAGE_API_BASE`（8000），检查 `imgWeb` 字段；
3. **Neo4j 断开**：列表/搜索返回 503，检查 `kg.py` 连接与 `NEO4J_URI`；
4. **问答超时**：LLM 推理慢，需 120s 超时与校园网连通；
5. **审核引擎不可用**：评论/图片回退待审，检查 `CONTENT_REVIEW_ENABLED` 与 MySQL 配置表。

排查工具：`GET /api/health`、`run_project_tests.py`、`test_image_api.py`、浏览器直接访问图片 URL。

#### Q5：你负责模块的关键文件和配置有哪些？

**答：**

| 类型 | 路径 |
|------|------|
| 以图搜图后端 | `server/image_search.py`、`build_image_index.py` |
| 以图搜图前端 | `SearchPage.ets`、`MuseumService.searchByImage()` |
| 多服务配置 | `entry/.../Constants.ets`（`API_BASE`、`IMAGE_API_BASE`、`QA_API_BASE`） |
| 联调文档 | `server/09_联调说明.md`、`服务器端/backend/Web组对接文档.md` |
| 测试脚本 | `run_project_tests.py`、`run_local_api_tests.py` |

#### Q6：以图搜图和文字搜索在后端处理上有什么区别？

**答：** 文字搜索在 MySQL 上做 `LIKE` 模糊匹配；以图搜图先做**视觉特征向量检索**，再在专题范围内回表补全详情。前者适合「知道名字」，后者适合「看到类似器型/纹饰但不知道名称」的场景，两者互补。
