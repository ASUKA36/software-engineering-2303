## 三、本周会议决议

### 3.1 组间功能联调总目标

第十三周核心任务由「单机各跑各的」转为**端到端组间联调**，验收以下三条业务链路在同一套服务器数据环境下可演示：

| 编号 | 联调链路 | 涉及组 | 验收标准 |
|------|----------|--------|----------|
| L1 | 文物浏览：服务器数据 → ② Web / ④ App 展示 | ①②④ | 列表、详情、搜索、图片加载无阻塞 |
| L2 | UGC 审核：②④ 提交 → ⑤ 审核 → ②④ 回显 | ②④⑤ | 待审不可见、通过后公开展示、拒绝有原因 |
| L3 | 智能问答：③ 服务 → ② Web 嵌入 → ④ App 调用 | ②③④ | Web 页内可问答；App 调同一套 API 获回答与溯源 |

**联调原则**：阻塞项当日在群内 @责任组 响应；接口变更须同步更新 README 与对接说明。

### 3.2 审核接口实现与 Web / App 对接

组会确认 ⑤ 提供、②④ 消费的**审核相关接口**如下，本周必须完成联调冒烟：

**（1）UGC 提交（②④ 各自实现，写入共用表）**

| 接口 | 方法 | 说明 |
|------|------|------|
| `/api/comments` | POST | 提交评论，`audit_status=pending`，`source=web\|app` |
| `/api/uploads` | POST | 提交图片上传，同上 |

提交成功后返回 `contentId`；前端**不得**将待审内容插入公开展示列表。

**（2）审核状态查询（⑤ 提供或经 ② 代理，②④ 调用）**

| 接口 | 方法 | 说明 |
|------|------|------|
| `/api/audit/status/{contentId}` | GET | 返回 `pending / approved / rejected` 及 `reject_reason` |
| `/api/audit/my-pending` | GET | 当前用户提交的待审/已审列表（可选） |

**（3）后台审核操作（⑤ 内部，审核员登录后使用）**

| 接口 | 方法 | 说明 |
|------|------|------|
| `/api/admin/audit/pending` | GET | 待审队列，含 `source` 字段区分 web/app |
| `/api/admin/audit/{contentId}/approve` | POST | 通过，写 `audit_records` |
| `/api/admin/audit/{contentId}/reject` | POST | 拒绝，必填 `reject_reason` |

**（4）联调流程（与第十二周 3.4 节一致）**

```
用户(②Web/④App) → POST 评论/上传 → pending
                → 公开展示区不渲染该条
⑤ 审核员 → 待审队列 → approve/reject
②④ → GET /audit/status/{contentId} 或列表刷新 → 仅 approved 公开展示
```

**分工约定**：

- **陶湘园（⑤）**：落实上述 admin 与 status 查询接口；确保 `comments`、`uploads`、`audit_records` 表字段与第十二周 3.5 节一致。  
- **万玉贤（②）**：Web 评论/上传表单对接提交与状态轮询；登录前校验 `users.status` 及 `restrict_comment` / `restrict_upload`。  
- **薛度扬（④）**：App 评论/上传对接同一套接口；`ApiClient` 中审核相关路径与 ② 保持一致（Base URL 可共用 ② 后端或经 ② 代理 ⑤）。

### 3.3 知识问答迁移至 Web 并为 App 提供接口

原 ③ 独立部署的问答能力，组会决议**以 Web 为主要入口对外呈现**，App 通过统一 REST 接口消费，避免 ②④ 各自直连 ③ 不同版本。

**（1）架构调整**

```
                    ┌─────────────────┐
  Web 用户 ────────→│  ② Web 前端      │
                    │  （问答页/浮窗）   │
                    └────────┬────────┘
                             │ POST /api/qa/ask
                    ┌────────▼────────┐
  App 用户 ────────→│  ② Web 后端      │────→ ③ 问答服务（意图/RAG/溯源）
  （ApiClient）     │  （问答 API 网关） │
                    └────────┬────────┘
                             │ 图谱检索
                    ┌────────▼────────┐
                    │  ① 图谱检索 API  │
                    └─────────────────┘
```

- **③ 保留**问答核心逻辑（意图识别、图查询生成、LLM 调用、来源拼装），不对外直接暴露给 App。  
- **② 后端**新增问答代理层，对外提供**唯一** `/api/qa/*` 接口；Web 前端与 ④ App 均调用该地址。  
- ③ 与 ② 之间采用内网 HTTP 或同机调用，地址写入 ② 后端配置，不写入 App 常量。

**（2）对外统一问答接口（② 提供，Web + App 共用）**

| 接口 | 方法 | 请求体 | 响应要点 |
|------|------|--------|----------|
| `/api/qa/ask` | POST | `{ "question": "...", "sessionId": "可选" }` | `answer`、`sources[]`（实体名、详情链接）、`hasData` |
| `/api/qa/health` | GET | — | 服务可用性，供 App 启动检测 |

**响应示例**：

```json
{
  "answer": "该文物收藏于史密森尼博物馆……",
  "hasData": true,
  "sources": [
    { "title": "青花瓷瓶", "artifactId": "obj_123", "url": "http://{server}/artifacts/obj_123" }
  ]
}
```

无图谱事实时：`hasData=false`，`answer` 为固定提示文案，禁止 LLM 编造。

**（3）Web 端迁移内容**

- 在 ② 增加「知识问答」入口（独立页面或全局浮窗组件）。  
- 前端仅调用 ② 的 `/api/qa/ask`，展示回答 Markdown/纯文本及可点击溯源链接。  
- 原 ③ 独立调试页保留为开发用途，演示与答辩以 Web 嵌入版为准。

**（4）App 端接入方式**

- `Constants.ets` 中问答 Base URL 与文物接口一致，指向 ② 后端。  
- 新增 `QAService.ets`（或扩展 `ApiClient`）：`askQuestion(question: string)` → POST `/api/qa/ask`。  
- 详情页或 Tab 增加「问一问」入口；展示 `answer` + `sources` 列表，点击跳转文物详情。

**分工约定**：

- **张芷淇（③）**：提供 ③ 内部问答编排接口供 ② 调用；保证服务器环境下 RAG + 溯源稳定；配合 ② 完成至少 3 类问题联调。  
- **万玉贤（②）**：实现 `/api/qa/ask` 网关与 Web 问答 UI；文档化请求/响应格式。  
- **薛度扬（④）**：App 问答页/组件对接 ② 接口；真机验证与 Web 同问同答一致性。

## 四、对接问题与解决方案汇总

| 问题 | 提出组 | 决议 |
|------|--------|------|
| App 与 Web 审核接口路径不一致 | ④ | 统一走 ② 后端或同一 Base URL；路径以 ② README 为准 |
| 问答原先仅 ③ 本地可测，Web 无入口 | ②③ | 问答迁移至 Web；③ 作为内部服务，② 对外网关 |
| App 不应配置多个后端地址 | ④ | 文物、用户、审核、问答均指向 ② `API_BASE_URL`（② 再代理 ③⑤） |
| 待审评论在 Web 列表闪现 | ② | 提交后仅写 pending，列表接口默认过滤非 approved |
| 问答溯源链接 App 无法打开 | ④ | `sources[].url` 使用服务器文物详情 deep link 或 App 内路由 |
