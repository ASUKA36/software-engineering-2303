### 3.2 各组使用知识图谱与数据库的统一方法

经组会讨论，明确**禁止** ②③④ 各自直连 Neo4j 或 MySQL；所有业务子系统须按下列统一路径访问数据：

| 消费方 | 访问方式 | 说明 |
|--------|----------|------|
| ② Web 知识服务 | 调用 ① 提供的 REST 只读 API（或经 ② 后端代理 ①） | 文物列表/详情/筛选/搜索走关系库接口；可视化关系图走图谱关系查询接口 |
| ③ 知识问答 | 调用 ① 封装的**图谱检索 API** | 意图→Cypher/SPARQL 由 ③ 内部生成，但**执行查询仅通过 ① 受控接口**，不暴露无鉴权图库端口 |
| ④ 掌上博物馆 | **优先**调用 ② 的同一套 REST API | 与 Web 共用文物与用户接口，避免双源；`Constants.ets` 中 `USE_MOCK=false` 时指向 ② 后端 |
| ⑤ 后台管理 | 管理侧读写 MySQL 业务表；图库修正经 ① 同步接口触发 | 避免 ⑤ 与 ① 双写破坏一致性 |

**统一约定**：

1. **文物主数据**：只读场景统一经 ① API 或 ② 代理 ①，不得重复爬取馆网。  
2. **图谱查询**：③ 与 ② 可视化均通过 ① 的 `图谱关系查询` 封装接口，入参/出参格式由第一组文档化。  
3. **环境配置**：各组 `.env` / 常量文件中数据库地址、API Base URL 以第一组发布的联调地址为准；变更须群内同步。  
4. **缓存与版本**：① 数据更新后发布版本号；②③ 据此失效本地缓存（若已实现）。

### 3.3 知识图谱在其他组的调用具体流程

组会确认以下**标准调用链路**（写入各组 README / 接口文档）：

**链路 A：Web / App 文物浏览**

```
用户 → ②/④ 前端 → ② 后端 GET /api/artifacts[/{id}|/search]
                 → ① 文物只读 API → MySQL（明细）+ 可选关联实体
```

**链路 B：Web 可视化 / 问答图谱检索**

```
用户 → ②/③ → ① GET /api/graph/neighbors 或 /api/graph/query
           → Neo4j（子图/路径）→ 返回节点边 JSON
```

**链路 C：知识问答 RAG**

```
用户问题 → ③ 意图识别 & 实体链接
        → ③ 生成图查询语句
        → ① 图谱检索 API 执行 → 事实子图 + 溯源字段
        → ③ 拼装 Prompt → LLM → 回答 + 来源标注
```

**链路 D：后台数据修正**

```
管理员 → ⑤ 后台 → MySQL 业务表 CRUD
                → 触发 ① POST /api/sync/graph（或等价同步任务）
                → Neo4j 增量更新
```

各组负责人确认上述链路满足本子任务需求；③ 张芷淇、② 万玉贤须在 **5 月 30 日前** 完成与 ① 图谱 API 的联调冒烟。

### 3.4 后台管理中 Web 组与 App 组审核流程对接

针对 ②④ 用户评论、上传图片等 UGC 功能，组会统一**审核闭环**如下：

| 步骤 | 责任方 | 动作 |
|------|--------|------|
| 1 | ② 或 ④ | 用户提交 UGC，写入业务表，`audit_status = pending`（待审） |
| 2 | ② 或 ④ | **不展示**待审内容；仅向提交者返回「已提交，审核中」 |
| 3 | ⑤ | 审核员在待审队列查看；自动审核（敏感词/图片）可先过滤 |
| 4 | ⑤ | 人工通过 → `audit_status = approved`；拒绝 → `rejected` 并记录原因 |
| 5 | ② 或 ④ | 轮询或 Webhook/消息通知获取审核结果；**仅 approved** 内容公开展示 |
| 6 | ④ | 审核通过后可触发 HarmonyOS 本地通知（选做） |

**接口约定（⑤ 提供，②④ 调用）**：

- `GET /api/admin/audit/pending` — 审核员拉取待审列表（⑤ 内部）  
- `GET /api/audit/status/{contentId}` — ②④ 查询单条内容审核状态  
- Web 与 App **共用同一套** `comments`、`uploads`、`audit_records` 表，通过 `source` 字段区分来源（`web` / `app`）。

**账号与权限**：前台用户表与管理员表继续隔离；②④ 登录校验走统一 `users` 表；封禁/限权状态由 ⑤ 维护，②④ 登录或发帖前须校验用户 `status`。

### 3.6 知识图谱服务器部署计划（第十三周执行）

组会决议：**下一周（第十三周）将知识图谱整体接入组内联调服务器**，供 ②③④⑤ 各子系统统一调用，结束各组本地库/本地 API 分散联调的状态。

**部署范围**

| 组件 | 部署内容 | 说明 |
|------|----------|------|
| MySQL | 文物明细、博物馆、用户及 UGC 等业务表 | 与本地已验证 schema 一致，含第十二周字段更新 |
| Neo4j | 全量三元组与实体关系 | 与 MySQL 文物数据保持同步 |
| ① 数据服务 | 文物只读 API、图谱检索 API、图库同步接口 | 作为各组访问图谱与数据库的**唯一服务端入口** |
| 静态资源 | 文物图片目录（或对象存储路径） | 与 CSV 中 `image_path` 映射一致 |

**部署原则**

1. **统一入口**：服务器部署完成后，各组 `.env` / `Constants.ets` 中的 `API_BASE_URL`、数据库连接地址一律指向服务器地址，不再各自维护本地 Neo4j/MySQL。  
2. **先部署后切换**：第十三周前半段由第一组完成服务器环境搭建与数据迁移；后半段各组分批切换接入并冒烟验证。  
3. **安全约束**：Neo4j、MySQL **不对公网开放直连端口**；②③④⑤ 仅通过 ① 封装的 REST API 访问；服务器防火墙仅放行必要的服务端口。  
4. **版本同步**：部署完成后第一组在群内发布**服务器 API 文档、Base URL、数据版本号**；各组切换前确认版本一致。

### 3.7 文物图片上传服务器（解决原图加载慢问题）

**问题背景**：联调测试中发现，② Web 与 ④ App 若直接使用 CSV 中的 `image_url`（海外博物馆原站链接）加载文物图片，存在明显延迟：跨境网络不稳定、部分馆方 CDN 限速、详情页原图体积较大，导致列表首屏与详情页图片加载时间常超过 **5～10 秒**，影响演示与用户体验。

**组会决议**：将爬虫阶段已下载至本地的文物原图（与 CSV 中 `image_path` 对应）**一并上传至组内联调服务器**，由服务器统一提供静态图片访问，各端**优先使用服务器图片地址**，海外原站 `image_url` 仅作溯源备用。

**实施方案**

| 项目 | 约定 |
|------|------|
| 图片来源 | ① 爬取阶段本地下载的原图文件（非缩略图） |
| 服务器目录 | 按博物馆分子目录，如 `/static/images/{museum}/{object_id}.jpg`，与 CSV `image_path` 规则一致 |
| 数据库字段 | `artifacts` 表新增或启用 `image_server_url`；API 返回时**优先**填服务器地址 |
| 访问方式 | `GET /static/images/...` 或经 ①/② 静态资源网关代理；支持浏览器/App 直接 `<img>` 加载 |
| 原站链接 | `image_url` 保留，用于详情页「查看来源」跳转，**不作为默认展示图** |

**接口返回约定（②① 文物 API）**

```json
{
  "objectId": "obj_12345",
  "title": "...",
  "imageUrl": "http://{server}/static/images/smithsonian/obj_12345.jpg",
  "imageOriginalUrl": "https://museum.example.org/..."
}
```

- 前端（Web/App）统一使用 `imageUrl`（服务器地址）渲染列表与详情；  
- `imageOriginalUrl` 可选展示为「原馆来源」外链。

**预期效果**

| 场景 | 改造前（海外原站） | 改造后（服务器托管） |
|------|-------------------|----------------------|
| Web 列表首屏（20 张缩略/卡片） | 常 > 8 秒 | 目标 ≤ 2 秒（内网/校园网） |
| App 详情页高清图 | 常 > 5 秒，偶发失败 | 目标 ≤ 1.5 秒 |
| 弱网/演示环境 | 易超时、占位图多 | 稳定可演示 |

**第十三周执行节点（纳入 3.6 部署）**

| 时间节点 | 事项 | 负责人 |
|----------|------|--------|
| 5 月 27 日前 | 全量原图上传服务器并完成路径校验（与 `object_id` 一一对应） | 郭晨沛 |
| 5 月 28 日前 | ①/② API 返回 `imageUrl` 切换为服务器地址；更新字段说明文档 | 郭晨沛、万玉贤 |
| 5 月 30 日前 | ② Web、④ App 完成图片加载回归；确认列表/详情无明显卡顿 | 万玉贤、薛度扬 |
