## 三、本周会议决议

### 3.1 用户与角色需求

组会确认平台主要角色及诉求，作为各子系统需求边界：

| 角色 | 主要诉求 | 涉及子系统 |
|------|----------|------------|
| 访客/注册用户 | 浏览文物、检索、可视化、问答、（可选）收藏评论 | ②③④ |
| 系统管理员 | 用户与权限、数据维护、系统参数 | ⑤ |
| 内容审核员 | 审核 UGC，维护内容安全 | ⑤；与 ②④ 联动 |
| 数据管理员 | 文物与三元组维护、导入导出 | ⑤；与 ① 联动 |

### 3.2 各子系统功能性需求确认

**（1）① 知识图谱构建**

- 爬取至少 3 家指定博物馆中国文物信息，字段含名称、原图、年代、类型、材质、介绍、详情 URL 等；UTF-8 CSV + 字段说明。  
- 清洗：标准化、去重、图片有效性校验。  
- 三元组建模：实体（Artifact、Museum、Dynasty、Artist、Location 等）与关系（收藏于、创作于、属于朝代、材质为、类型为等）；参考 CIDOC-CRM 思想。  
- 双层存储：Neo4j + MySQL；支持增量更新策略（本阶段可先实现全量）。

**（2）② Web 知识服务**

- 列表/卡片浏览、多维筛选排序、详情页、相关推荐；简单/高级/图谱类查询；关系图、时间轴、地图、统计等可视化（实现项在详细设计中裁剪固定）。  
- 用户注册登录与基础资料；UGC（评论等）按选做条款，若实现须对接 ⑤ 审核。

**（3）③ 知识问答**

- **RAG 架构**：意图/实体 → 图查询 → 事实子图 → LLM 生成 → **来源标注**。  
- 覆盖任务书所列主要简单问答类型；图谱无数据时**明确提示**，禁止伪造。  
- 复杂多轮、反馈等按选做处理。

**（4）④ 掌上博物馆**

- HarmonyOS + ArkTS；至少包含文物列表、详情、搜索。  
- 扩展：收藏、评论、上传等按进度选做；用户字段与 Web 端对齐方向提前预留。

**（5）⑤ 后台管理**

- 管理员独立账号；RBAC（超级管理员、审核员、数据管理员等）。  
- 用户管理、待审队列、文物 CRUD、三元组维护、操作日志；备份监控等可简化。

### 3.3 非功能性需求

| 类别 | 要求 |
|------|------|
| 性能 | 课堂演示场景下主要页面与查询响应可接受；具体指标各组在设计中自定 |
| 安全 | 密码安全存储、后台权限控制、接口基本校验 |
| 可维护性 | 模块划分清晰、配置与代码分离、README 与部署说明完整 |
| 数据质量 | CSV 编码 UTF-8；爬取统计与完整性报告；溯源 URL 可追溯 |

### 3.4 跨子系统需求约束

1. **单一数据事实来源**：文物主数据由 ① 产出，②③④ 不得重复爬馆网。  
2. **接口形态待定**：第十周概要设计中确定 REST API 边界及 ② 是否作为 ④ 的数据代理。  
3. **UGC 审核闭环**：若 ②④ 实现评论/上传，须写入待审状态并由 ⑤ 审核后公开展示。  
4. **问答溯源**：③ 回答须附带数据来源与详情链接，与 ① 元数据字段对齐。
