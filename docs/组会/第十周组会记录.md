## 三、本周会议决议

### 3.1 系统总体架构

采用**前后端分离**与**数据层分层**结构：

| 层次 | 组成 | 说明 |
|------|------|------|
| 表现层 | Web 前端、HarmonyOS App、后台管理前端 | 各子系统独立 UI |
| 服务层 | ① 数据服务 API、② Web 后端、③ 问答服务、⑤ 管理后端 | REST 接口；禁止业务端直连图库 |
| 数据层 | MySQL（业务表）、Neo4j（三元组） | 由 ① 牵头构建与同步 |
| 外部服务 | LLM API、（可选）图像审核 API | ③⑤ 按需调用 |

**依赖关系**：构建 → 存储 → 服务 / 问答 / 移动 → 后台监管。

### 3.2 各子系统模块设计要点

| 子系统 | 核心模块 |
|--------|----------|
| ① 知识图谱构建 | 爬虫、清洗、建模、对齐与补充、入库与同步 |
| ② Web 知识服务 | 浏览与检索、查询服务、可视化、用户中心 |
| ③ 知识问答 | 问题理解、图谱检索、生成与溯源、安全兜底 |
| ④ 掌上博物馆 | 展示与搜索、用户与内容（选做）、ApiClient 对接 |
| ⑤ 后台管理 | 权限与账号、用户与审核、数据管理、操作日志 |

各模块功能要点与《项目管理计划》第四章保持一致，详细接口在联调阶段细化。

### 3.3 子系统服务边界与对接说明

组会决议输出《子系统服务对接说明》初版，明确「谁提供什么、谁向谁要什么」：

| 提供方 | 主要服务 | 消费方 |
|--------|----------|--------|
| ① | 文物只读查询、图谱关系查询、元数据与溯源 | ②③④⑤ |
| ② | 浏览检索 API、可视化数据、（可选）用户认证与 UGC 上报 | ④、最终用户 |
| ③ | 问答接口、无数据兜底响应 | ②④ |
| ⑤ | 审核结果、用户封禁/限权状态 | ②④ |

**关键约定**：

1. ②④ **优先共用**文物与用户相关接口，避免 App 与 Web 双源。  
2. ③ **禁止直连** Neo4j；图查询经 ① 受控 API 执行。  
3. ⑤ 管理侧读写 MySQL；图库修正经 ① 同步，避免双写。  
4. UGC 流程：`pending` → ⑤ 审核 → `approved` 后公开展示。

### 3.4 数据与存储设计要点

**关系型库（MySQL）**：用户与角色、文物明细、博物馆、朝代、媒体资源、评论/上传、审核记录、操作日志等。

**图库（Neo4j）**：节点 Artifact、Museum、Dynasty、Artist、Location；关系收藏于、创作于、属于朝代、材质为、类型为等。

**CSV 规范**：遵循任务书附录 2；UTF-8 编码；提交字段说明与爬取说明。

### 3.5 设计报告（项目管理计划）定稿

组会确认以《项目管理计划》作为课程设计**概要设计报告**主体，包含：

1. 绪论（目的、内容与目标）  
2. 需求分析摘要（引用需求规格说明书）  
3. 系统总体设计与子系统划分  
4. 功能与模块设计  
5. 技术方案与关键技术  
6. 数据与存储设计要点  
7. 进度计划与人员分工  
8. 测试计划  

文档由薛度扬牵头汇总，各组负责人审核本子系统章节；**5 月 12 日前** 完成 v1.0 定稿并建立文档维护表。

### 3.6 测试策略（概要）

采用黑盒为主、关键模块白盒为辅；重点验证爬虫入库、权限控制、问答溯源、核心检索与可视化。测试用例编号从 TC-01 起，覆盖爬虫、Web、可视化、问答、后台、审核等模块（详见《项目管理计划》第八章）。
